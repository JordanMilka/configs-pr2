# depgraph

Инструмент визуализации графа зависимостей пакетов Alpine Linux (apk).
Практическая работа, вариант 8.

## 1. Общее описание

`depgraph` - консольное приложение на Python 3.9+, которое получает
зависимости пакета из репозитория Alpine Linux. Менеджеры пакетов и
сторонние библиотеки не используются: только стандартная библиотека
(`urllib`, `tarfile`, `re`, `argparse`).

Реализовано:

- **Этап 1** - чтение и проверка конфигурации из YAML-файла.
- **Этап 4** - обратные зависимости: какие пакеты зависят от заданного
  (тот же обход BFS над «перевёрнутым» репозиторием).
- **Этап 3** - граф транзитивных зависимостей (обход BFS с рекурсией),
  фильтр по подстроке, обработка циклов, тестовый режим с файлом
  описания графа.
- **Этап 2** - сбор данных: загрузка индекса репозитория (`APKINDEX.tar.gz`)
  по URL, разбор формата apk и вывод прямых зависимостей пакета заданной
  версии.

Каждый этап запускается **отдельной командой** (подкомандой):

| Команда                           | Что делает                               |
|-----------------------------------|------------------------------------------|
| `python -m depgraph stage1`       | выводит параметры конфигурации           |
| `python -m depgraph stage2`       | выводит прямые зависимости пакета        |
| `python -m depgraph stage3`       | строит и выводит граф транзитивных зависимостей |
| `python -m depgraph stage4`       | выводит обратные зависимости пакета (кто от него зависит) |

Следующие этапы (граф, обратные зависимости, Mermaid) добавляются
отдельными коммитами и своей командой `stage5`.

Как это работает. Репозиторий Alpine хранит для каждой архитектуры файл
`APKINDEX.tar.gz` - tar-архив со сжатым текстовым индексом `APKINDEX`.
Приложение скачивает его, находит запись с нужными `P:` (имя) и `V:`
(версия) и выводит поле `D:` (зависимости) этой записи.

Структура репозитория:

```
src/depgraph/
  cli.py          командная строка: команды этапов, коды завершения
  stage1.py       этап 1: вывод параметров конфигурации
  stage2.py       этап 2: прямые зависимости пакета
  stage3.py       этап 3: граф транзитивных зависимостей
  stage4.py       этап 4: обратные зависимости
  graph.py        BFS с рекурсией, фильтр, поиск циклов
  reverse.py      источник обратных зависимостей
  apk_source.py   сопоставление зависимостей пакетам индекса Alpine
  file_repo.py    тестовый репозиторий (файл описания графа)
  config.py       загрузка и проверка конфигурации
  simple_yaml.py  разбор плоского YAML
  repository.py   загрузка и распаковка APKINDEX.tar.gz
  apk_index.py    разбор формата APKINDEX, поиск пакета
  errors.py       исключения
tests/            модульные тесты (unittest)
examples/         примеры конфигураций
Makefile          запуск и тесты
```

## 2. Описание функций и настроек

### Настройки (YAML-файл)

Все шесть параметров обязательны; неизвестные ключи запрещены.

| Ключ               | Тип    | Описание                                    |
|--------------------|--------|---------------------------------------------|
| `package_name`     | строка | Имя анализируемого пакета                   |
| `repository`       | строка | URL каталога репозитория с `APKINDEX.tar.gz` (с архитектурой, например `https://dl-cdn.alpinelinux.org/alpine/v3.20/main/x86_64`) либо URL самого файла; в тестовом режиме - путь к файлу описания графа |
| `test_mode`        | bool   | `true` - `repository` это путь к файлу тестового репозитория (`stage3`, `stage4`); `false` - URL |
| `package_version`  | строка | Точная версия пакета, как в индексе: `1.36.1-r29`. Берите в кавычки (`"1.10"`), иначе YAML превратит её в число |
| `ascii_tree`       | bool   | Вывод зависимостей в виде ASCII-дерева (этап 5) |
| `filter_substring` | строка | Пакеты, имя которых содержит подстроку, не учитываются (этап 3). Пустая строка `""` - без фильтра; без пробелов |

Параметр `ascii_tree` проверяется, но будет использован на этапе 5.
`filter_substring` применяется командами `stage3` и `stage4`. Команда `stage2`
работает только с URL (`test_mode: false`); в тестовом режиме она
подсказывает использовать `stage3`.

Поддерживаемое подмножество YAML (`simple_yaml.py`): строки
`ключ: значение`, комментарии `# ...`, `true`/`false`, `null`, числа,
строки без кавычек, в `"двойных"` (экранирование как в JSON) и в
`'одинарных'` кавычках. Отступы, вложенность, списки, `[...]`, `{...}` и
повторяющиеся ключи дают ошибку с номером строки.

Пример: `examples/config.yaml`.

### Командная строка

```
python -m depgraph КОМАНДА [-c PATH]
```

| Команда  | Описание                                                    |
|----------|-------------------------------------------------------------|
| `stage1` | этап 1: вывести параметры конфигурации (`ключ: значение`)   |
| `stage2` | этап 2: вывести прямые зависимости пакета заданной версии   |
| `stage3` | этап 3: построить граф транзитивных зависимостей (BFS)      |
| `stage4` | этап 4: вывести обратные зависимости пакета                 |

Команда обязательна. Опции указываются **после** команды:

| Опция            | Описание                                       |
|------------------|------------------------------------------------|
| `-c`, `--config` | путь к YAML-файлу (по умолчанию `config.yaml`) |
| `-h`, `--help`   | справка (`depgraph -h` или `depgraph stage2 -h`) |

Коды завершения: `0` - успех; `2` - ошибка конфигурации или аргументов;
`3` - ошибка получения данных (сеть, архив, нет пакета или версии).

### Что выводит stage1

Все шесть параметров в формате `ключ: значение`; сеть не используется:

```
package_name: busybox
repository: https://dl-cdn.alpinelinux.org/alpine/v3.20/main/x86_64
test_mode: false
package_version: 1.36.1-r29
ascii_tree: true
filter_substring: musl
```

### Что выводит stage2

Прямые зависимости печатаются так, как они записаны в индексе (поле `D:`),
по одной на строку: обычные пакеты (`musl>=1.2.5`), виртуальные имена
(`so:libc.musl-x86_64.so.1`, `cmd:sh`, `pc:zlib`) и ограничения версий
(`=`, `<`, `>`, `<=`, `>=`, `~`). Конфликты (записи, начинающиеся с `!`)
зависимостями не считаются и не выводятся.

### Что выводит stage3

Граф в порядке обхода BFS: для каждого пакета указан уровень (расстояние
от корня) и его прямые зависимости. Далее выводятся:

- транзитивные зависимости (все достижимые пакеты, кроме корня);
- циклические зависимости (каждый цикл как `A -> B -> A`);
- пакеты, исключённые фильтром (если задана подстрока);
- зависимости, которых нет в репозитории (листья графа).

Правила построения графа:

- **BFS с рекурсией.** Функция `visit_level` (`graph.py`) обрабатывает
  один уровень графа и вызывает сама себя для следующего уровня.
  Вершина добавляется в обход один раз, поэтому циклы не приводят к
  бесконечной рекурсии. Глубина рекурсии равна числу уровней графа;
  если она превышает лимит Python, выводится ошибка.
- **Фильтр.** Пакет, имя которого содержит `filter_substring`
  (с учётом регистра), пропускается вместе со всеми своими
  зависимостями. Пакет остаётся в графе, если до него есть другой путь
  мимо исключённых. Если подстроке соответствует сам корневой пакет,
  выводится ошибка.
- **Циклы.** Ищутся обходом в глубину без рекурсии: один цикл на каждое
  обратное ребро, одинаковые циклы считаются один раз. Зависимость
  пакета от самого себя - цикл из одного пакета (`A -> A`).
- **Реальный репозиторий.** Зависимости вида `so:libc.musl-x86_64.so.1`
  или `cmd:sh` сопоставляются пакетам, которые предоставляют это имя
  (поле `p:`). Прямое имя пакета важнее виртуального; если подходит
  несколько пакетов, берётся первый в индексе. Для корня используется
  точная версия из конфигурации, для остальных пакетов - запись из
  индекса. Зависимость пакета от собственного виртуального имени
  пропускается. Загружается один индекс (`repository`), поэтому
  зависимости от пакетов другого репозитория (например, от `main` при
  анализе `community`) попадают в список ненайденных.

### Что выводит stage4

Обратные зависимости пакета - пакеты, которые зависят от него напрямую
или через другие пакеты. Для их поиска используется тот же рекурсивный
обход BFS (`graph.build_graph`), что и на этапе 3: класс `ReverseSource`
(`reverse.py`) переворачивает зависимости всего репозитория, и «детьми»
пакета становятся зависящие от него пакеты. Поэтому фильтр, уровни и
обработка циклов работают так же, как на этапе 3.

Вывод: обход BFS с уровнями (`<-` ведёт к зависящим пакетам), список
зависящих пакетов, циклы и пакеты, исключённые фильтром.

Особенности:

- В тестовом режиме пакет может быть только упомянут как зависимость
  (не описан отдельной строкой) - обратные зависимости для него
  находятся.
- В реальном репозитории анализируется весь индекс, поэтому для
  популярных пакетов (например, `musl`) список очень большой.
  Версия корня (`package_version`) должна существовать в индексе, но на
  результат не влияет: зависимости считаются по имени пакета. Если у
  имени несколько версий, берётся запись, стоящая в индексе первой.
- Зависимости только из загруженного индекса учитываются; пакеты из
  других репозиториев (`community`) здесь не видны.

### Тестовый режим (`test_mode: true`)

Вместо URL в `repository` указывается путь к файлу описания графа.
Формат - строка на пакет:

```
A: B C
B: D
D:
```

Имя пакета - одна или несколько **больших латинских букв**; после
двоеточия через пробел перечислены зависимости (список может быть пустым).
Пустые строки и текст после `#` игнорируются. Версия пакета
(`package_version`) в тестовом режиме не используется. Ошибки формата
выводятся с номером строки (неверная строка, строчные буквы или цифры в
имени, повторное описание пакета, пустой файл).

Готовый файл `examples/test_repo.txt` содержит семь случаев. Для этапа 3
есть конфигурации `examples/config_test_*.yaml`, для этапа 4 -
`examples/config_reverse_*.yaml` (см. примеры ниже).

### Модули и функции

- `graph.py`: `build_graph(source, root, substring)` - построение графа;
  `visit_level` - рекурсивный BFS; `find_cycles`; класс
  `DependencyGraph`.
- `apk_source.py`: класс `AlpineSource` - сопоставление зависимостей
  пакетам индекса Alpine.
- `file_repo.py`: `load_file_source(path)`, `parse_repo_text(text)` -
  тестовый репозиторий.
- `stage3.py`: `run(config, stream)`, `open_source`, `format_graph`.
- `reverse.py`: класс `ReverseSource` - обратные зависимости.
- `stage4.py`: `run(config, stream)`, `format_graph`.
- `repository.py`: `load_packages(url)` - скачать, распаковать и разобрать
  индекс; `index_url`, `download`, `extract_index`.
- `apk_index.py`: `parse_index(text)`, `parse_dependency(token)`,
  `find_package(packages, name, version)`; классы `Package`, `Dependency`.
- `config.py`: `load_config(path)`, `validate(raw)`, класс `Config`.
- `simple_yaml.py`: `parse_yaml(text)`.
- `stage1.py`: `run(config, stream)`, `format_value`.
- `stage2.py`: `run(config, stream)`, `fetch_package`,
  `format_dependencies`.
- `cli.py`: `main(argv)`, `build_parser`; словарь `STAGES` связывает имя
  команды с модулем этапа (у модуля есть `SUMMARY` и `run`).

### Обработка ошибок

Конфигурация: нет файла, не UTF-8, некорректный YAML, неизвестные и
отсутствующие ключи, неверный тип или формат параметров (все проблемы
выводятся сразу, код 2).

Данные (код 3), этапы 3-4: корневой пакет не найден, корень исключён
фильтром, граф слишком глубокий, ошибка формата файла тестового
репозитория (с номером строки), файл репозитория нельзя прочитать.

Данные (код 3), этапы 2-3: недоступный сервер, HTTP-ошибка (например, 404), таймаут,
слишком большой файл, повреждённый или не-gzip архив, нет файла `APKINDEX`
в архиве, пакет не найден, версия не найдена (в сообщении перечислены
доступные версии).

## 3. Сборка и тесты

Сборка не нужна, зависимости устанавливать не нужно.

Linux/macOS (с make):

```
make stage1    # этап 1 с examples/config.yaml
make stage2    # этап 2 (нужен доступ в интернет)
make stage3 CONFIG=examples/config_test_cycle.yaml
make stage4 CONFIG=examples/config_reverse_diamond.yaml
make stage2 CONFIG=my.yaml
make test      # запуск тестов
```

Без make (в том числе Windows PowerShell):

```
$env:PYTHONPATH = "src"      # Linux/macOS: export PYTHONPATH=src
python -m depgraph stage1 -c examples/config.yaml
python -m depgraph stage2 -c examples/config.yaml
python -m depgraph stage3 -c examples/config_test_mode.yaml
python -m depgraph stage4 -c examples/config_reverse_diamond.yaml
python -m unittest discover -s tests -v
```

Тесты не требуют интернета: индекс собирается в памяти и отдаётся
локальным HTTP-сервером на `127.0.0.1`; тестовый режим читает файлы из
`examples/`.

### Этап 4: примеры с тестовым репозиторием

Все примеры используют `examples/test_repo.txt`; различаются
`package_name` и `filter_substring` в конфигурации. Вывод получен
запуском команд.

**Ромб** (`config_reverse_diamond.yaml`, пакет `D`): у `D` напрямую зависят `B` и `C`, а `A` зависит от него через оба пути и выводится один раз.

```
$ python -m depgraph stage4 -c examples/config_reverse_diamond.yaml
Пакет: D
Обратные зависимости (порядок BFS, [уровень], '<-' ведёт к зависящим пакетам):
  D [0] <- B, C
  B [1] <- A
  C [1] <- A
  A [2] <- (никто не зависит)
Пакеты, зависящие от D (3): B, C, A
Циклические зависимости: нет
```

**Цикл** (`config_reverse_cycle.yaml`, пакет `E`): `E` лежит на цикле `E -> F -> G -> E`: зависящие пакеты `G`, `F`, цикл выведен, обход завершается.

```
$ python -m depgraph stage4 -c examples/config_reverse_cycle.yaml
Пакет: E
Обратные зависимости (порядок BFS, [уровень], '<-' ведёт к зависящим пакетам):
  E [0] <- G
  G [1] <- F
  F [2] <- E
Пакеты, зависящие от E (2): G, F
Циклические зависимости (1):
  E <- G <- F <- E
```

**Зависимость от самого себя** (`config_reverse_self_loop.yaml`, пакет `J`): `I` зависит от `J` и от самого себя.

```
$ python -m depgraph stage4 -c examples/config_reverse_self_loop.yaml
Пакет: J
Обратные зависимости (порядок BFS, [уровень], '<-' ведёт к зависящим пакетам):
  J [0] <- I
  I [1] <- I
Пакеты, зависящие от J (1): I
Циклические зависимости (1):
  I <- I
```

**Фильтр** (`config_reverse_filter.yaml`, пакет `L`): подстрока `B`: `KB` и `BK` зависят от `L`, но исключены; `K` зависит от `L` напрямую и остаётся.

```
$ python -m depgraph stage4 -c examples/config_reverse_filter.yaml
Пакет: L
Обратные зависимости (порядок BFS, [уровень], '<-' ведёт к зависящим пакетам):
  L [0] <- K
  K [1] <- (никто не зависит)
Пакеты, зависящие от L (1): K
Циклические зависимости: нет
Исключено фильтром 'B': BK, KB
```
